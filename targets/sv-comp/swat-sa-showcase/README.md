# swat-sa-showcase

Small, self-contained programs where SWAT's static pre-analysis decides whether SWAT gets a
verdict, or at least how fast. SA here means everything that comes from cfg-extraction: the
graph's pruning and slicing, loop summaries, loop-state matching and the property pre-check. Each
task is a plausible piece of a real program (a bank CLI, an order importer, a thermostat, ...), not
a synthetic family. Most are based on a swat-benchmarks family whose measurements show the effect
(`../swat-benchmarks/RESULTS.md`), with one task per feature, sized like the family's largest
variant.

Layout as in `swat-benchmarks`: `java/<suite>/<task>_{true,false}/Main.java` with a `.yml` next to
it. `_true` is SAFE, `_false` is VIOLATION, and the two differ only in the bug. The suite `nre`
uses `no-runtime-exception.prp`, all others `valid-assert.prp`. The sources are generated by
`scripts/gen.py` (one template per pair).

## Tasks

### valid-assert

| task | feature | based on | the bug |
|---|---|---|---|
| `pruning/bank-cli` | reachability pruning over a dispatcher with exact receivers: 12 command classes with 3-5 branches each cannot reach the assert in `Withdraw` | `dispatcher/ifchain`, `virtual-dispatch/local` | the funds check leaves out the fee |
| `pruning/order-import` | pruning of handlers of implicit exceptions (`ArrayIndexOutOfBoundsException` from 11 table lookups, `ArithmeticException` from a division); each handler logs with 3 branches and skips the line | `error-handling/bounds`, `arith` | a discount table holds 120 for 12 |
| `pruning/sensor-monitor` | context-sensitive pruning of a helper (`classify`) that is dead in report mode (8 calls, 3^8 paths) but live on the alarm path | `dead-callees/shared` | one escalation step has no cap |
| `slicing/backup-resume` | relevance slicing: a 1000-iteration loop whose input-dependent branch only logs, counts and fills a scratch array; the assert reads the input | `relevance/loop-helper`, `scratch-array` | a missing clamp lets the checkpoint counter overflow |
| `slicing/feature-flags` | relevance slicing of 16 independent flag branches (2^16 paths) that only register and log | `irrelevant-prefix/count` | only port 0 is replaced by the default |
| `summaries/subscription-invoice` | loop summary of a diamond with a nested condition (`day % 7 < 5`) in a 1000-iteration loop | `loop-summary/count-below`, `count-even` | the welcome credit is also granted after long trials |
| `summaries/loan-schedule` | closed form of a counting loop up to an input bound whose body also calls a logger (relevance-gated summary) | `loop-summary/count-up-log` | the term limit was raised to 480 months, the credit line still assumes 360 |
| `loop-states/thermostat` | loop-head state matching with only live locals (`temp`, a fresh input per iteration, is dead at the head) and a head in a callee | `loop-liveness/dead-input`, `loop-frames/callee-loop` | the relay is not switched off |

### valid-assert, several asserts of which only one can fail

| task | feature | asserts | the bug |
|---|---|---|---|
| `multi/payroll` | pruning: an audit mode with 3^9 paths reaches none of the four asserts | gross >= base, tax <= gross, net >= 0, bonus <= cap | the referral bonus is added after the cap |
| `multi/elevator` | loop-state matching in an unbounded event loop (floor, direction, door: 36 states) | in the shaft (in `move`), not moving with the door open | the door button opens the door while the car moves |
| `multi/meter-billing` | loop summaries: a diamond over 672 15-minute slots (nested condition) and a counting loop for the standing charge | slots <= 672, standing charge <= 31 days, bill >= 0 | the goodwill credit is granted to every late installation |

### no-runtime-exception (`nre`)

| task | feature | the bug |
|---|---|---|
| `nre/token-bucket` | the pre-check's value analysis: an unbounded event loop with a symbolic token count, but nothing that can throw (every object is created before use, nothing indexes or divides by a variable) | the audit object is never created: `NullPointerException` on the first oversized request |
| `nre/session-store` | pruning with the pre-check's site facts: of nine commands, only the two that index the session table (`id % slots.length`) contain a site that may throw | a negative session id: `ArrayIndexOutOfBoundsException` |
| `nre/average-order` | loop summary of a diamond in a 1000-iteration loop, feeding a division | a cutoff >= 1000 counts no order: `ArithmeticException` |
| `nre/traffic-light` | loop-state matching in an unbounded loop over a cycle of phase objects | the walk phase (added later) has no successor: `NullPointerException` |

The assertions are the program's own sanity checks, and the bugs are the kind that happen: a fee
left out, a typo in a table, a missing cap or clamp, a rule applied too broadly, a limit raised in
one place only, a state not reset, an object never created.

Not included: the soundness suites (`sa-soundness`, `relevance-soundness`, `loop-summary-soundness`,
`loop-state`; they check consistency, not benefit), the families where SA does not help
(`dispatcher/loop`, `virtual-dispatch/factory`, `exception-dispatch`, gauntlet `return`/`throw`),
and hand-written facts (`user-facts`, `extractor-facts`), which need `--user-facts` and a person's
annotations rather than SWAT's own analysis.

## Build, check, run

```bash
cd targets/sv-comp/swat-sa-showcase/scripts
./gen.py              # regenerate the sources and .yml files
./build.sh            # javac --release 8 -g:source,lines, classes next to the sources
./check_labels.py     # replays each task's inputs (header comment) against a stub Verifier
CONFIGS="sa nosa" ./run_configs.sh     # one run per configuration (TIMEOUT 300, WORKERS 14)
../../swat-benchmarks/scripts/compare.py ../../runs/run_A ../../runs/run_B   # valid-assert only
```

`check_labels.py` checks that each VIOLATION task's inputs fail its assert (an uncaught
RuntimeException for `nre`), that the paired SAFE task does not fail on them, and that the all-zero
run (SWAT's round 0) fails nowhere. Why each SAFE task is SAFE for every input is in its header
comment.

`run_configs.sh` runs both properties and refuses to start while another SV-COMP run is live.
Configurations:

| config | flags |
|---|---|
| `sa` | the default configuration plus `--sa-no-runtime-exception` (SA pruning under no-runtime-exception is opt-in in the harness) |
| `nosa` | no SA feature at all: `--no-sa --no-loop-summaries --no-property-precheck --config-file sv-comp-noSA.cfg` (see "Runs without SA" in `SWAT/CLAUDE.md`) |
| `noprecheck`, `noslice`, `nosum`, `nostate` | `sa` without the property pre-check, slicing, loop summaries or loop-state matching |

`compare.py` reads only valid-assert results; for `nre`, run a copy with `valid-assert` replaced by
`no-runtime-exception`.

- **Every task that needs SA fails exactly in the configurations that remove its feature:**
  pruning (`sensor-monitor`, `payroll`) only in `nosa`; slicing (`backup-resume`, `feature-flags`)
  in `noslice`; summaries (`subscription-invoice`, `meter-billing`, `average-order`) in `nosum`;
  loop-state matching (`thermostat`, `elevator`, `traffic-light`) in `nostate`. `loan-schedule`
  needs both summaries and slicing: its loop body calls a logger, so the summary is only honored
  once the relevance analysis confirms the loop changes nothing relevant (`mergedConditional`).
- **Violations SWAT finds only with SA:** `backup-resume_false`, `subscription-invoice_false`,
  `meter-billing_false`, `average-order_false`. `loan-schedule_false` is found without summaries
  only after about 259 rounds, close to the limit: UNKNOWN in `nosum` on 2026-11-21, found there now.
- **Several asserts:** pruning, summaries and loop-state matching work with several target points
  as with one. With SA, `payroll_true` takes 61 rounds;
  without, its 3^9 audit paths take the whole budget.
- **No-runtime-exception:** `token-bucket_true` is SAFE in one round with SA, also without the
  pre-check step itself: the graph's site facts come from the same value analysis, find no site
  that can throw, and both sides of the first branch are pruned. Without any SA its unbounded loop,
  with a symbolic token count, cannot be finished. `session-store` gets the same verdicts without
  SA, but with 144 rounds instead of 9.
- **Pruning alone is not decisive in `bank-cli`, `order-import` and `session-store`:** it cuts the
  rounds by 10-20x, but rounds take only about 0.4 s here, so SWAT also finishes without it. More
  handlers or fields would make them time out without SA.
- **SA's fixed cost** is the extraction, 6-7 s per task: the small VIOLATION tasks are faster
  without SA.

### Where the time goes

- **`subscription-invoice_true`: 48 s for one round**, almost all of it one solver query. The loop's
  branches are merged, so the assertion's flip query is sliced: the explorer solves the full query
  first (all loop constraints kept: UNSAT in 0.006 s), then the sliced one (UNSAT in 33-34 s, 153M
  rlimit units). That query holds `total` as 1000 nested `ite(day >= trialDays, total + c, total)`
  over 32-bit vectors, and Z3 needs that long to show that no `trialDays <= 90` makes it fall below
  500. Rebuilt by hand: 0.4 s for 300 iterations, 25 s for 1000; over Integers 46 s, no better.
  Without summaries every query is tiny, but each `trialDays` is its own path (50 rounds try 0 to
  48 and 256 before the CPU limit). A closed form for such guarded accumulators (the condition is
  monotone in the counter) would make the proof instant.
- **`session-store_true`: 72 s for 9 rounds**, 59 s of it in two UNSAT queries (about 30 s each,
  240M rlimit units) that show `(id & 0x7fffffff) % slots.length` is in range: the table's length is
  an input (`capacity`, clamped), and a remainder by a symbolic divisor is hard for Z3. With a
  fixed table size they would be trivial.

### Limitations found while building the tasks

- **Any array on the heap stops loop-state matching.** `LoopStateMatcher` requires every value on
  the shadow heap to be concrete, and `AbstractArrayValue.isSymbolic()` counts an array as symbolic
  whenever its formula has a variable. Every array's formula starts as a named solver array
  (`amgr.makeArray(name, ...)`), so even a constant table (`static final int[] SECONDS = {30, 5,
  40, 5, 20}`, never written) makes every state unhashable ("Not hashed: symbolic value"). The
  first `traffic-light` (a duration table indexed by the phase) was UNKNOWN in every configuration
  for this reason; it now uses a cycle of phase objects. Fixing it means asking an array whether
  any element (or its length) is symbolic rather than its formula.
- **A diamond whose side declares a local and tests `&&` was not merged.** The first
  `meter-billing` had `int time = slot % 96; if (time >= 32 && time < 80)` inside the loop's `if`:
  the walk showed about 5 merged branches per run instead of about 2000, and the task was UNKNOWN
  in every configuration. With the condition inlined into one comparison
  (`slot % 96 / 32 == 1`) the loop is merged and the task is SAFE in 3 rounds. Both changes were
  made together, so which of the two blocked the merge is not known.
- **The property pre-check's value domain is constants only** (no ranges, no refinement by
  branches): it cannot prove an array index or divisor computed from input safe, even behind a
  clamp (`if (capacity < 1 || capacity > 1024) capacity = 64; new int[capacity]` is "array size
  may be negative"). So it proves programs that never index or divide by a variable, and the
  tasks above are shaped accordingly.
